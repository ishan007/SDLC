

Capture the CI baseline

ops/pipeline/run-timings.csv has one row per step, and the conclusion column repeats on every row of a run. Treat run_number as the unit.

1. Group rows by run_number. A run's conclusion is the value on its rows. Check that it is the same on every row of the run and report any run where it is not.
2. Success rate = successful runs / total runs (not successful rows / total rows).
3. Per-run duration = sum of that run's step durations. Report median and p90 separately for successful and failed runs, because a failed run may stop early and look faster.
4. The three slowest steps by median, using successful runs only.
5. State the number of runs and the date range.

Write this as a script and save it to submission/risk-audit/ci-metrics.py (or .sh) so I can rerun it. Show the script and its output.

Then, run gh run list --workflow ci.yml --limit 100 --json conclusion,createdAt,updatedAt and report the same success rate and duration for the real .github/workflows/ci.yml runs. If there is no remote or no runs, say so.

Label the CSV numbers clearly as the planned pipeline's history, not this repository's real CI.

Output: numbers into submission/risk-audit/measurement-plan.md. The two numbers the plan asks you to capture from this file are CI duration and success rate.
